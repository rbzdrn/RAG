RAG 核心流程解析

结合图书馆比喻：从建立索引到搜索回答

阶段一：建立索引 离线准备 · 闭馆时进行

这个阶段用户看不到，发生在后台。系统正在把原始的笔记，加工成方便快速检索的格式。

现实比喻 代码函数 具体发生什么
1. 拆书 chunker.py 按标题切出 父块（整章节），把正文切出 子块（小段落）。
2. 做目录卡 embedder.py 给每一个 子块 算向量，变成类似“指纹”的目录卡。
3. 存卡片柜 store.py 把子块存入向量库，建好 BM25 关键词索引，等待被搜索。
4. 存原书 store.py 把父块纯文本放在档案库，暂不参与检索，只等被回填。

阶段二：查找与回答 在线服务 · 用户提问时

你在输入框里敲下问题，系统开始这三步连招：

1

查卡片（定位子块）

系统把你的问题去子块库里对比（向量检索）。找到最匹配的一个小段落。
retriever.py → search()

2

取原书（回填父块）

系统看这个子块身上带的 parent_id，去父块库把这一整章的大块内容抽出来。
retriever.py → get_parents()

3

总结回答（生成输出）

系统把抽出来的父块全文交给大模型（AI），大模型阅读后，生成流式答案返回给你。
generator.py → build_context() → stream()

一图看懂数据流转

// 离线建索引 原文件 ──切块──> 子块 (Chunk) ──算向量──> 向量库 ===> 用于“查得准” └──切块──> 父块 (Parent) ──纯文本──> 档案库 ===> 用于“给得全” // 在线查找与回答 用户提问 ──算向量──> 搜 子块 ──拿到ID──> 取 父块 ──发给──> 大模型 (LLM) ──> 最终回答
核心秘诀：Small-to-Big
因为子块小，所以“检索准”（能定位到具体段落）；
因为父块大，所以“生成全”（大模型不会断章取义）。
